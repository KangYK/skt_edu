PRD는 누구를 위해 무엇을 만들고 어떻게 완료 여부를 판단할지 정리하는 문서입니다.

## 1. 배경 · 문제
고객에게 납품한 웹 애플리케이션의 오류·문의 접수와 유지보수를 한곳에서 관리합니다. 고객은 접수와 처리 상황을 확인하고, 내부 담당자는 배정된 고객사의 문의를 처리합니다.
기존 AI 표준팀 홈페이지와 별도 프로젝트입니다. 이번 목표는 실제 문의를 저장·조회하는 서비스입니다. 가상 데이터를 사용하는 시연 화면도 별도로 제공합니다.

## 2. 목표와 성공 기준
| 목표 | 확인 방법 |
|---|---|
| 접수부터 완료까지 추적 | 생성된 접수 번호로 재로그인 후 조회 가능 |
| 고객사 정보 분리 | 다른 고객사의 문의·댓글·첨부 파일에 서버 접근 거부 |
| 담당자 업무 처리 | 배정·댓글·상태 변경이 저장되고 이력에 남음 |
| 고객의 자가 해결 | 사용 가이드·유지보수 범위·공지로 이동 가능 |
| 시연과 운영 구분 | 시연 배지와 가상 데이터, 운영과 분리된 저장소 |
성공 기준은 구현 후 검증할 목표이며 현재 달성된 상태가 아닙니다.

## 3. 대상 사용자
| 역할 | 조회 범위 | 주요 행동 |
|---|---|---|
| 고객 | 본인이 접수한 문의 | 접수, 공개 댓글 작성, 상태 확인 |
| 고객사 담당자 | 소속 고객사의 전체 문의 | 고객사 요청 확인·협의 |
| 내부 유지보수 담당자 | 배정된 고객사의 문의 | 분류·배정된 작업 처리·내부 메모 |
| 관리자 | 전체 문의 | 고객사·제품·계정·배정·권한 관리 |
고객사 담당자는 소속 고객사의 계약·가이드만 조회합니다. 내부 메모는 고객과 고객사 담당자에게 노출하지 않습니다. 계정 생성 시 사용자가 고객사·역할을 임의로 선택해 권한을 얻을 수 없도록 합니다.

## 4. 범위
### 실제 서비스
- 이메일·비밀번호 로그인, 비밀번호 재설정, 회사 계정 로그인 지원 목표.
- 고객사별 사용자 초대와 제품 접근 범위 설정.
- 오류·문의 접수, 필터·검색·상세, 공개 댓글·내부 메모, 첨부 파일.
- 담당자 배정, 처리 상태와 변경 이력, 장애·점검 공지, 사용 가이드, FAQ.
- 고객사·제품별 유지보수 범위 표시. 계약 기준은 운영자가 입력하며 임의의 서비스 수준이나 응답 시간을 약속하지 않음.
### 시연
- 가상 고객사·제품·문의와 역할 전환을 제공하되 ‘시연’으로 표시.
- 운영 데이터 및 운영 인증과 분리. 역할 전환은 운영 서버에서 제공하지 않음.
- 시연 구현 완료를 실제 인증·보안·배포 완료로 표현하지 않음.
### 확장 항목
- 기존 고객 관리 시스템 연동. 시스템과 API가 미정이므로 연결 지점만 설계하고 실제 연동 완료로 표시하지 않음.
- 이메일 등 외부 알림은 제공업체 선정 후 연결.

## 6. 화면 구성
로그인 → 역할별 대시보드 → 접수/문의 목록 → 문의 상세.
데스크톱은 좌측 메뉴와 상단 검색·계정, 본문 요약 및 문의 목록으로 구성합니다(가정). 모바일은 접이식 메뉴와 카드 목록을 사용합니다.
고객 대시보드: 새 문의 버튼, 내 접수 건수, 답변 대기, 최근 처리 현황, 장애·점검 공지, 자주 찾는 가이드.
담당자 대시보드: 배정 문의, 우선순위, 고객 회신 대기, 최근 변경 내역.
문의 상세: 접수 정보 → 상태·담당자 → 공개 대화 → 변경 이력. 내부 메모는 별도 구획.

## 7. 콘텐츠 상세
### 7-1. 팀 소개
제목: 접수부터 해결까지, 함께하는 고객지원.
소개: 납품한 웹 애플리케이션의 문의와 오류를 접수하고 안정적인 사용을 위한 유지보수를 지원합니다.
주요 업무: 오류 분석·복구, 사용 문의 안내, 유지보수 범위 검토, 점검 공지.
### 7-2. 접수 양식
필수: 접근 가능한 제품, 유형(오류/사용 문의/개선 요청), 제목, 상세 내용.
오류 선택 시: 발생 시점, 재현 순서, 기대 결과·실제 결과, 영향 범위를 안내. 비밀번호나 인증 토큰 입력 금지 안내.
고객사·작성자 식별자는 로그인 세션에서 서버가 결정합니다.
첨부의 허용 형식·개수·용량은 운영 전 확정. 안전한 파일 검사와 권한 있는 다운로드를 적용합니다.
### 7-3. 상태 흐름 (제안)
접수 → 확인 중 → 처리 중 → 고객 확인 대기 → 완료.
추가 정보 필요 시 ‘정보 요청’, 계약 범위 검토 시 ‘범위 검토’를 사용합니다. 재문의는 기존 문의 재개와 이력으로 관리합니다.
상태 전환은 내부 담당자와 관리자에게 허용하며 고객은 댓글과 재개 요청을 할 수 있습니다. 완료 기준과 재개 기간은 운영 전 확정합니다.
### 7-4. 문의·운영 안내
이메일 예시: team@example.com. 지원 시간·응답 기한은 미정. 실제 운영 연락처와 계약 기준을 확인한 뒤 적용합니다.
예시 자료는 가상 고객사 A/B, 예시 제품 1/2 등으로 작성합니다.

## 9. 반응형 · 접근성
375px 이상에서 가로 스크롤 없는 구성. 모바일 표는 문의 카드로 전환. 터치 버튼은 충분한 크기로 표시하고 키보드 포커스·명시적 입력 라벨·오류 안내를 제공합니다. 상태는 색만으로 구분하지 않습니다.

## 10. 기술 조건
실제 서비스의 인증·권한·저장은 index.html 하나만으로 구현하지 않습니다. HTML/CSS/JS 화면, 서버 API, 관계형 데이터베이스, 비공개 첨부 저장소를 분리합니다.
### 제안 구조 (확정 전)
- 프런트엔드: HTML/CSS/JavaScript 기반, 로그인·대시보드·목록·상세 화면.
- 서버: Node.js 기반 API 제안. 기술·배포 환경은 구현 전 확인.
- 데이터: PostgreSQL 등 관계형 DB 제안, 영구 저장·마이그레이션·백업·복원.
- 인증: 검증된 인증 솔루션을 통해 이메일/비밀번호와 회사 계정 OIDC/SAML을 연결. 회사 로그인 제공업체·테넌트 설정 미정.
- 세션: 서버 검증, 보안 쿠키, 만료·로그아웃 처리. 권한은 UI 숨김뿐 아니라 모든 API에서 검증.
### 데이터 모델
customers(고객사), users(사용자), memberships(고객사 소속·역할), products(제품), assignments(담당자 배정), tickets(문의), comments(공개/내부), attachments(첨부), ticket_events(변경 이력), guides, notices, contracts.
고객사 소유 데이터에는 customer_id를 포함합니다. 문의·댓글·첨부·검색·내보내기 모든 경로에서 고객사와 역할 검사를 적용합니다. 연결된 제품·문의의 고객사가 일치하는지도 확인합니다.
### 운영 조건
최소 권한, 감사 이력, 요청 제한, 입력 검증, 업로드 검사, 보관·삭제 정책과 복원 절차. 실제 고객 데이터 투입 전 권한·백업 검증 필요. 비밀 키는 소스나 GitHub에 넣지 않습니다.

## 14. 구현 결과와 확정된 변경
- 사용자 확인: 회사 로그인·배포 환경은 아직 미정이며 로컬 실행부터 진행.
- 별도 DB 설치가 필요 없는 Node.js 24 + SQLite 단일 서버 구성으로 구현. 다중 서버 운영 시 PostgreSQL 이전 검토.
- HTML/CSS/JS 화면, 이메일 로그인, 계정 초대·재설정, 네 역할 권한, 고객사 분리, 문의·댓글·내부 메모·첨부·이력·관리 화면 구현.
- 시연 포트 4311, 실제 저장 포트 4310. 데이터베이스·세션 쿠키 분리.
- 회사 계정 로그인, 이메일 자동 발송, 외부 고객 관리 시스템 연동, 악성코드 스캐너, 공개 운영 배포는 미연결. 운영 준비 항목은 README 참고.
- 서버 통합 테스트 14개 통과. 브라우저에서 접수·답변·상태 변경·담당자 배정 확인. 1280px/375px 화면 검증.
- ‘크리에이티브 스튜디오’라는 후속 메시지는 이름 변경/디자인 변경/새 프로젝트 중 적용 방식 확인 대기. 현재 고객지원팀 이름 유지.
